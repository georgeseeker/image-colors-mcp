# image-colors MCP

让 AI 助手精确知道一张图用了哪些颜色。为"照着现有图做设计"这类任务写的。

## 为什么需要它

直接让模型看图报色,拿到的回答是"偏灰的深蓝"这种量级。`#282c34` 和 `#2b303b` 在模型眼里是同一个东西,而在设计里它们不是。想拿到可信的 hex,传统做法是截图落盘、写脚本采样,每取一次色要三次工具调用外加一个临时脚本;而且就算清单拿到了,颜色和元素仍然对不上——不知道哪个是背景、哪个是描边、哪个是那排五个圆点。

这个 MCP 把这两件事各压成一次调用。

## image_colors

```
image_colors(path, min_blob_px=40, max_candidates=48)
```

返回整张图的颜色清单,画布色已经排除。

```json
{
  "size": [1718, 1006],
  "has_alpha": false,
  "canvas": {"hex": "#ffffff", "rgb": [255,255,255], "hsl": [0,0,100],
             "excluded_px": 1523097, "corner_agreement": "4/4"},
  "colors": [
    {"hex": "#8faadc", "rgb": [143,170,220], "hsl": [218,52,71], "count": 12410,
     "blobs": 5, "sizes": [2482,2482,2482,2482,2482],
     "largest": {"bbox": [213,233,58,53], "area": 2482,
                 "fill": 0.807, "solidity": 0.99, "thickness": 24.57},
     "shape_hint": "filled"}
  ],
  "dropped_aa": {"count": 5, "hexes": ["#cee1f3", "#e0ecf7"]},
  "examined_candidates": 85
}
```

`bbox` 一律是 `[x, y, w, h]`,图像像素坐标,原点在左上角。画布色取四角像素的众数,`corner_agreement` 告诉你四个角里有几个同意这个判断——不是 `4/4` 就说明图有边框、圆角裁切或者渐变背景,画布判断要打个折扣。

几何字段是给"把颜色对应回元素"用的。`blobs` 是这个颜色在图里形成了几个连通块,`sizes` 按降序列出其中最大的八个的面积。五块面积完全相同,基本可以断定那是一排相同的元素;`sizes` 只给前八个,所以 `blobs` 超过 8 时两者长度不等。`fill` 是最大那块面积除以外接矩形面积,圆约等于 0.785(也就是 π/4),正方形是 1.0,细长或中空的值明显更低。`solidity` 是轮廓面积除以凸包面积,凸的填充形状——旋转过的也算——接近 1.0,而环形、L 形、箭头会低得多。`thickness` 是 `2*面积/周长`,约等于平均线宽,是区分色块和细线最直接的量:两像素的线读出来是 2.0,直径五十像素的圆是 24.57。`shape_hint` 只是把 `fill` 和 `thickness` 粗判一下方便扫读,别当结论用。

`count` 是精确像素数,只为了让你知道哪个颜色更"重",工具本身不输出比例。

## image_pixel

```
image_pixel(path, x, y, tolerance=10)
```

取一个点的颜色,落点允许粗略。

```json
{"seed": [231,256], "hex": "#8faadc", "rgb": [143,170,220], "hsl": [219,52,71],
 "region": {"area_px": 2488, "bbox": [212,232,60,55], "distinct": 4},
 "dominant_share": 0.9976, "flat": true}
```

落点是**种子**:从它开始长出所在的平坦区域,返回那个区域的众数——出现次数最多的精确值,保证在图中真实存在,而不是平均值。所以你不必精确瞄准,大致指到色块上就行。

`flat` 是 `dominant_share >= 0.95` 的简写。它为 false 说明落点踩在渐变或者边缘上,那个 hex 不能当作单一设计色使用,换一个点重取。

`tolerance` 是逐通道阈值,而且是**对比种子本身**而不是对比相邻像素,所以渐变无法一步一步把区域带跑。默认 10 是刻意收紧的:18 会把 `#121212` 和 `#1C1C1C` 合并,而在暗色 UI 里它们是两个不同的面。

## 设计决定

这些都不是拍脑袋定的,每一条都有实测支撑。

**精确枚举,绝不聚类。** 一张矢量图上通常只有几百到几千个独特色,真调色板就是频率最高的那几个。k-means 在实测图里把 8 个真色全部带偏,最差 ΔE 0.148;median cut 有一半槽位浪费在抗锯齿灰上。聚类在这里只会引入误差。

**候选按几何筛挑选,而不是"取前 48 再过滤"。** 黑底白字的图里,黑白之间的抗锯齿灰大约有 250 级、每级数千像素,取前 48 会被灰占满,真色根本没机会被检查。

**两道抗锯齿筛。** 几何筛(色块至少 `min_blob_px`)能抓住文字周围的小碎片,但抓不住大色块边缘的**长条带**——那些轻松超过阈值。所以还有第二道:判断这个颜色能否被两个更常见的颜色线性混合解释。实测抗锯齿色的混合误差不超过 0.57,真色最小 10.54,**18 倍分离度**,阈值取 2 到 4 都很稳。

**近重复合并。** 渐变靠近端点的那几步,距离端点只有几个 RGB 单位,落在混合检测的端点护栏之内,但它和端点视觉上本来就分不出来。

**取点用 floodFill,不用全图 mask。** 结果逐字节相同,0.30ms 对 52.87ms,而且耗时随色块大小增长,不随图片尺寸增长。

**先排除画布色再排序。** 提速 2.92 倍(1.7M 像素图)到 2.23 倍(27.7M 像素图)。

**`np.bincount` 被否掉了。** 它比 `np.unique` 慢 12 倍,因为每次调用都要分配并清零一个 134MB 的 2^24 桶直方图。

## 已知限制

**渐变会占满候选槽位。** 每个渐变步都是一个 1px 宽的窄条,面积足以通过几何筛,只能靠混合筛拒绝,而拒绝发生在选出 48 个之后,排在渐变后面的真实色可能被挤掉。渐变步的像素数通常远低于真实色,实际影响有限。

**`min_blob_px` 是绝对像素值,不随导出倍率缩放。** 同一份稿子的 1x 和 2x 版本可能给出不同结果。

**ICC 配置被忽略。** Display-P3 或 Adobe RGB 的 PNG 会按 sRGB 读,hex 有偏差;CMYK 是朴素转换,可能严重偏色。

**JPEG 基本不适用。** 平坦区域被蚊式噪声环绕,精确枚举的前提不成立。工具会返回空列表并附说明,而不是报错。

**同色的相邻区域会合并成一个连通块。** 蓝按钮放在蓝卡片上只算一个区域,区分不出这是两个元素。

**超大图慢。** 每个候选都要一次全图比较,`np.unique` 还会物化一份排序副本,8K 图首次调用可能要几十秒。结果按 `(路径, mtime, 参数)` 缓存,同一张图重复调用很快。

**`outline_relations`(自动识别"谁是谁的描边")第一版没有实现。** 用 bbox 嵌套做判据误报严重:一个颜色如果同时出现在页眉和页脚,它的 bbox 会横跨整图,于是"套住"图里每一个填充色。要做这件事需要真正基于 mask 的几何包含判定。

**格式覆盖有限。** EXIF 已经转正,但 16-bit PNG、调色板模式、以及 APNG/GIF/WebP 的多帧都没有特别处理,多帧只取第一帧。

## 安装

依赖 Pillow、numpy、opencv-python 和 mcp 官方 SDK。把仓库放在哪里都行,注册时给出绝对路径即可——解释器路径建议钉死,避免 PATH 漂移:

```json
"image-colors": {
  "type": "stdio",
  "command": "<python.exe 的绝对路径>",
  "args": ["<本仓库路径>/src/server.py"]
}
```

写进 Claude Code 用户级配置顶层的 `mcpServers`,或者直接用 `claude mcp add` 添加。注册后需要新开一个会话才会加载。
